# 30 天行動計畫與檢核

課堂完成不等於正式導入完成。將 Lab 結果轉成有負責角色、核准範圍與回復方式的任務，先試點再擴大。

## 四週導入工作表

| 期間 | 工作 | 完成證據 |
|------|------|----------|
| 第 1 週 | 盤點資源、角色與依賴，指定負責人，評估緊急存取 | 受控清冊、風險優先序、變更與溝通計畫 |
| 第 2 週 | 選兩個試點應用，導入 Gateway MI 與無金鑰驗證，Policy 先 Audit | 正負向呼叫結果、Audit 合規清單 |
| 第 3 週 | 設定每應用 TPM / quota、警示與預算；核准後收斂管理權 | 隔離測試、通知實測、角色複核紀錄 |
| 第 4 週 | 完成既有金鑰遷移，核准後導入 Deny，演練應變並移交維運 | 舊金鑰遭拒、例外清冊、演練缺口與營運排程 |

這是規劃範本，不保證 30 天即可完成。沒有緊急管理途徑時，先修復這項缺口；模型、網路或授權依賴未就緒時，不強行切換正式流量。

## 導入驗收清單

- [ ] 每個 AI 資源有負責人，金鑰與網路狀態均已確認。
- [ ] 一般應用走 Gateway，模型端只保留必要身分；直連正負向測試已完成。
- [ ] 本機金鑰停用已在資料平面驗證，未遷移例外有核准與複核日。
- [ ] 每個應用的 TPM / quota 已設定，限流來源與應用間隔離已確認。
- [ ] 日誌不記錄憑證與不必要內容，Token 統計與實際通知均已測試。
- [ ] 預算通知對象正確，團隊知道它不會自動停止花費。
- [ ] 管理角色符合任務，緊急帳號與 MFA 已驗證，回復計畫可用。
- [ ] Policy 範圍、排除項目與效果已測試，不把 Deny 當作自動修復。

## 三個桌上演練

只使用虛構事件與測試憑證，不上傳實際金鑰、個資或稽核紀錄。

| 情境 | 練習處置順序 | 驗收問題 |
|------|--------------|----------|
| Gateway 訂用金鑰疑似外洩 | 保留必要證據 → 暫停受影響測試訂用 → 輪替並安全重新配發 → 檢視流量 → 核准恢復 | 能否只處理單一應用，不影響其他訂用？ |
| Token 突增 | 確認來源與是否為重試迴圈 → 限制應用或測試訂用 → 調查排程與帳務 → 修正後恢復 | 能否區分 Gateway 限流與後端容量問題？ |
| 高權限帳號疑似遭入侵 | 啟動既有事件流程與可信管理途徑 → 保存稽核 → 由授權人員隔離身分並檢查角色異動 → 驗證恢復 | 緊急途徑是否可用？是否涵蓋根範圍提升存取？ |

真實事件依組織的通報、鑑識與核准流程處置，不以教材取代事件指揮。

上述金鑰情境可接續[模型 Key 與 APIM 訂用 Key 輪替演練](../key-rotation/)，實際驗證舊 Key 遭拒與替代 Key 可用。課堂時間有限時，採用[三個短 Demo](../short-demos/)；預期狀態碼不代表已實跑成功。

## 營運節奏

每週檢視異常用量、直連線索與未解釋的角色異動；每月複核額度、憑證與例外；至少每 90 天驗證緊急存取並複核管理權限。服務版本、授權或人員變更後，也應重新驗證。

對外分享只保留匿名化結論與改善事項，完整的清冊與證據保留在組織核准的位置。
